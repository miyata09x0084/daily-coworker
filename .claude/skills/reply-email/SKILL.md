# reply-email — メール返信案の作成

## 概要

貼り付けられたメールに対し、`.claude/skills/_shared/email-style.md`(文体ガイド)に基づいて返信案を1つ生成する。
Gmail への書き込みは一切行わない。返信案はテキスト提示のみで、送信はユーザー自身が行う。

## フロー

起動したらまず `.claude/skills/_shared/email-style.md` の存在を確認する。

- 存在しない → セットアップモード
- 存在する → 返信モード

## セットアップモード(初回のみ)

1. 「初回セットアップとして、過去の送信メールから文体を抽出します」と伝える
2. `mcp__claude_ai_Gmail__search_threads` で `in:sent` を検索し、直近の送信スレッドを取得する
3. `mcp__claude_ai_Gmail__get_thread` で送信メール本文を20〜30件分読む
   - ニュースレター転送・機械的な一行返信は分析対象から除外する
4. 以下の観点で文体を分析する:
   - 冒頭: 挨拶と感謝の入り方(表現の使い分けパターン)
   - 本文: 結論の置き方、1文の長さ、敬語レベル、段落の切り方
   - 結び: 締めのパターン、信頼感の出し方
   - 頻出フレーズと、逆に使っていない定型句
5. 分析結果を「文体ガイド案」として提示し、対話で修正する
   - 特に「感謝と信頼感のバランス」(感謝が過剰にならない加減、堅さとやわらかさの配分)は必ずユーザーに確認して言語化する
6. 承認を得てから `.claude/skills/_shared/email-style.md` に保存する
7. 返信対象のメールが既に貼られていれば、そのまま返信モードへ進む

### email-style.md の構造

```markdown
# メール文体ガイド
## 基本原則      # 感謝と信頼感を優先・バランスよく、を具体的な規範に言語化
## 冒頭の型      # 挨拶と感謝の入り方(実メール由来のパターン)
## 本文の型      # 結論の置き方、文の長さ、敬語レベル
## 結びの型      # 信頼感を残す締め方
## よく使う表現  # 実メールから抽出した頻出フレーズ
## 使わない表現  # 過剰な謙遜、テンプレ臭い定型句 など
```

### フォールバック

送信メールの取得に失敗した、または分析に足る件数(10件未満)しかない場合:
「自分らしいと思う返信メールを2〜3通貼ってください」と依頼し、貼られたメールから同じ観点で抽出する。

## 返信モード

1. `.claude/skills/_shared/email-style.md` を Read する
2. 貼られたメールを解析する:
   - 送り主とユーザーの関係性(文面の敬語レベル・呼称から推定)と、フォーマル/カジュアルの判定
   - メールの目的(依頼/質問/報告/日程調整/お礼 など)
   - 返信で答えるべき問い(漏らさず全部拾う)
3. 事前ヒアリング(必要な場合のみ): 次のいずれかに該当したら、返信案を書く前に質問する(最大3問)。本人にしか書けない中身を創作で埋めない
   - 返信に本人の判断・感情・固有の状況説明が必要で、元メールや会話から読み取れない
   - 関係性や前提が本文から読み取れない
   - ※日程確定・承知などの手続き的返信は該当しない(質問なしで直行)
4. 返信案を1つ生成する。構成の基本形:
   - 感謝(冒頭): 相手の連絡・対応への具体的な感謝。定型句で流さない
   - 本題: 答えるべき問いに結論ファーストで答える
   - 結び: 信頼感の残る締め(次のアクションの明示、相手への配慮)
5. セルフチェック: 提示前に文体ガイドの「品質基準」に照らして検証する。「答えるべき問い」は1問ずつ回答の有無を確認する
6. 提示フォーマットで出力する
7. フィードバックを受けて磨く。修正指示は自然言語でそのまま受け付ける

## 提示フォーマット

````markdown
## 返信案

```
(件名: Re: ...)

本文
```

**判断ポイント**: 1行目に質問カバレッジ(例: 質問カバレッジ: 3/3)。意図的に答えなかった問いは「2/3(納期の件は確認後に別途回答)」のように理由つきで示す。続けて迷った箇所を1〜2行添える(例: 日程提示は相手に委ねる形にしました)
````

## 制約

- Gmail への書き込み(下書き作成・送信・ラベル操作)は行わない
- 返信案は1案のみ。複数案は出さない
- email-style.md にない文体上の判断が必要になったら、その場でユーザーに確認し、確定した内容を email-style.md への追記として提案する
