# つたえログ

1対1のやりとりと「伝え方」を記録して、口約束の抜け漏れを防ぐローカル Web アプリ。
親と子、上司と部下、支える側と支えられる側、担当者と顧客 ——
**口頭で決まることが多く、催促が関係に響く関係**のための道具。

- 記録は**このパソコンの中だけ**に保存される（`data/tsutae-log/db.json`、git 管理外）
- サーバーは既定で `127.0.0.1` にしか bind しない
- 外部サービスへの通信は一切しない（CSP で `self` のみ許可）
- 依存パッケージ **ゼロ**。`npm install` は不要

## まず動かしてみる

```bash
cd webapp
npm run demo              # 架空のサンプルデータ入りで起動 → http://127.0.0.1:4173
npm run demo -- --lan     # 同じWi-Fiのスマホからも開ける（URLが表示される）
```

サンプルは一時ファイル（`/tmp/tsutae-log-demo.json`）に作られるので、本物の記録には触れない。

## 本番で使う

```bash
cd webapp
npm start                 # 空の状態から。記録は data/tsutae-log/db.json に貯まる
```

スマホから使いたいときは `TSUTAE_HOST=0.0.0.0 npm start`。
ただし**認証はない**ので、同じネットワークにいる端末からは誰でも読める。
つないでいる人が分かっているネットワークでだけ使うこと。

| 環境変数 | 既定値 | 意味 |
|---|---|---|
| `TSUTAE_PORT` | `4173` | 待ち受けポート |
| `TSUTAE_HOST` | `127.0.0.1` | `0.0.0.0` にすると同じネットワークの他端末からも見える（既定は不可） |
| `TSUTAE_DATA` | `data/tsutae-log/db.json` | 保存先ファイル（未指定なら既存の記録を探して引き継ぐ） |

テストは `npm test`（Node 標準の `node:test`、外部依存なし）。

操作をひとつずつ知りたい場合は **[使用手順書（MANUAL.md）](MANUAL.md)** を読んでください。

## コンセプト

**記録するのは相手のことではなく、こちらの伝え方。**

入力欄も、集計も、警告も、主語はすべて「伝えた側」に置いてある。
一度に何件渡したか、紙にしたか、急かさずに待てたか、相手の言葉で戻ってきたか。
できなかったことの一覧は作らない —— 作れば、いつか相手の目に入るからで、
その瞬間にこの道具は「見せられると嫌なもの」に変わって使えなくなる。

この立て付けは資料だけでなく**画面にも置いてある**（初回の「今日」、設定画面、記録フォームの書き方ヒント、
「次に話すこと」に畳んである伝え方の約束）。書いておかないと、使ううちに
「相手ができなかったことの台帳」へ戻っていくため。

だから設計上こうなる:

- 未完了が増えたときに疑うのは本人ではなく、**渡しすぎていないか**
- 日付を過ぎた件で出る言い方は、できていない事実に触れない（「いつやる？ 今日と明日ならどっち？」）
- 渡すカードには**過ぎた日付を一切載せない**。経過日数は記録者の画面にだけ残る
- 「伝え方の効き目」が測っているのは相手の能力ではなく、自分の渡し方

### 「通る条件」で持つ

相手の弱点ではなく、うまくいったときの条件を書く。
同じ観察でも、書き方の向きが変われば別の道具になる。

| こうすれば通る | だから道具がやっていること |
|---|---|
| 一度にひとつなら通る | 渡すのは3件まで（件数は設定で変えられる） |
| 時間があれば自分でできる | 日付は先に置く。当日に詰めない。催促の文言を出さない |
| 言葉でなら伝わる | 渡すのは図ではなく短い文。グラフは記録者だけが見る |
| 書いてあれば何度でも確かめられる | 口頭で終わらせず、かならず紙（カード）にする |

もうひとつの前提は、**記録は続かなければ意味がない**ということ。
必須項目は本文ひとつだけにしてあり、その日の様子や伝え方は未入力でも保存できる。
入力を強制すると、忙しい日から順に記録が途切れる。

### 記録の書き方

自由記述には、相手が読んで傷つく言葉を書かない。主語を自分にすると、
記録がそのまま次に直す場所になる。

| 書かない | こう書く |
|---|---|
| また忘れてた | 口頭だけで伝えた。紙は渡していない |
| 話が通じない | 一度に3件渡した。1件目しか残らなかった |
| やる気がない | 日付を当日に置いた。取りかかる時間がなかった |

## 画面

| 画面 | 役割 |
|---|---|
| 今日 | 今日かける声と、その言い方。抜け漏れ警告 |
| 記録する | やりとりの記録と、その場でのやくそく切り出し |
| やくそく | 未完了の一覧。緊急度順に並ぶ |
| 目標 | 長期目標・マイルストーン・停滞検知 |
| 見える化 | 記録カレンダー、その日の様子の推移、放置日数、伝え方の効き目 |
| 渡すカード | 相手に渡すプレーンテキスト（印刷・コピー可） |
| 設定 | 呼び名、しきい値、書き出し／読み込み |

### 抜け漏れをどう防いでいるか

1. **記録とタスク化を1画面にまとめた。** 別操作に分けると、記録した直後の「あれ頼んだんだった」が必ず落ちる
2. **期限のない約束を放置しない。** 一定日数たつと「日付を決めよう」と促す
3. **同時依頼の上限を設けた。** 超えたぶんは渡すカードにも載せない
4. **理解確認を3段階で記録する。** 「わかった？」と聞いただけでは伝わったと数えない
5. **伝え直しの回数を数える。** 3回を超えたら、回数ではなく伝え方を変える合図として出す

### 伝え方の効き目

決着した（完了 or 取り下げ）やくそくだけを母数に、工夫の有無で完了率を比べる。
片側が3件未満のときは**判定を出さない**。少ない件数から出た差を根拠にすると、
効いていないやり方を続けることになる。

## 構成

```
webapp/
├── server/
│   ├── index.js      起動（bind 先とデータ保存先の決定）
│   ├── app.js        HTTP・ルーティング・静的配信
│   ├── store.js      JSON 永続化（原子的置換・書き込み直列化）
│   ├── domain.js     入力検証とドメイン操作
│   ├── insights.js   集計・警告・見える化（数える場所はここだけ）
│   └── handoff.js    渡すカードと週次ふりかえりの文面生成
├── shared/           サーバーとブラウザが両方読む定義（定数・日付）
├── public/           画面（素の ES モジュール、ビルド不要）
├── tools/seed.js     架空のサンプルデータ
└── test/             node:test
```

集計はすべてサーバー側の `insights.js` が 1 回で出す。
画面ごとに数え直すと「ダッシュボードでは3件、カードでは2件」というずれが起きるため。

## API

Claude Code のスキルなど、外から読むための口も開けてある。

| メソッド | 経路 | 用途 |
|---|---|---|
| GET | `/api/state` | 全データ＋集計 |
| GET | `/api/insights` | 集計のみ |
| GET | `/api/handoff?nextTalkDate=YYYY-MM-DD` | 渡すカード |
| GET | `/api/review?format=markdown` | 週次ふりかえり |
| GET | `/api/export` | バックアップ用 JSON |
| POST | `/api/interactions` | やりとり（やくそく同時作成可） |
| POST/PATCH/DELETE | `/api/commitments[/:id]` | やくそく |
| POST/PATCH/DELETE | `/api/goals[/:id]` | 目標 |
| PATCH | `/api/settings` | 設定 |

## データを守る

保存先は 1 つの JSON ファイルで、書き込みは一時ファイル経由の原子的置換。
読めないファイルになっていた場合は `.broken-<時刻>` に退避してから起動する（上書きしない）。

とはいえローカルファイルなので、消えるときは静かに消える。
**設定 → バックアップ**から定期的に書き出しておくことを勧める。
